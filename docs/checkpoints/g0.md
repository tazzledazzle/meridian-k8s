## S0 outcome

- `ops.yaml` lists 36 operations. Floci serves 34. Two small custom backends serve the rest: `ec2-sim` for
  `ec2:DescribeInstanceTypes` and `pricing-facade` for `pricing:GetProducts`.
- The contract probe has 37 checks. Floci passed 35 and failed 2. The routed run passes 37 of 37.
- No full EC2 simulator was needed. `CreateFleet` reaches `running` on Floci.
- Floci runs EC2 and EKS in mock mode and has no Docker socket. Nodes come from `node-registrar` and KWOK.

## What was harder than expected

1. **Pricing.** Real Karpenter rejected the first facade twice: it lower-cases filter names, and it fails if its bare-metal query returns nothing.
2. **Nodes without machines.** Floci launches no machines in this mode. `node-registrar` turns each instance into a KWOK Node, and every workload must tolerate KWOK's taint.
3. **The isolated network.** k3s will not start on an `internal` Docker network without a default route (fixed inside the container), and the system pods raced the image import and tried to pull (fixed by mounting the images at startup).
4. **Offerings versus types.** Floci's `DescribeInstanceTypeOfferings` lists 19 types, and only `m5.large` and `t3.medium` are also in the catalog. Karpenter launches only types present in both, so it never considered `c5.large`. C5 passes with a `t3.medium` and `m5.large` pool. Moving `DescribeInstanceTypeOfferings` to `ec2-sim` would fix the cause, but it changes the table you approved (bead `meridian-17s.64`).
5. **k3d's Docker socket.** The stricter audit found that k3d's own helper container mounts the host Docker socket and was on the gate network. My Task 15 check had missed it. `k3d-up.sh` now removes the helper after the cluster is created.
6. **k3d's API port.** k3d configures a host binding that Docker does not open on an internal network. The audit now flags it, and `--api-port 127.0.0.1:0` removes the exposure on any other network.

## Limits

- Not validated against real AWS. No claim of parity.
- Not covered: rebalance and scheduled-change events, a node with several pods, and the real two-minute spot grace period (the gate uses 10 s).
- The gate ran on one machine (Docker Desktop, macOS, arm64). A Linux and amd64 run and a fresh-runner CI run are Task 17.
- The golden file records every client of the gateway (Karpenter, `simctl`, `node-registrar`, the test's own queries), not Karpenter alone.
  `ec2:RunInstances` is Karpenter's own dry-run authorization check (EC2NodeClass validation, v1.14.1).

- **C5 shows the cheaper type was chosen, not where the price came from.** Karpenter ships a static price table with the same ordering, so C5 would also pass if the pricing facade were ignored. `pricing:GetProducts` is called (C8 records it), but a stronger proof would serve inverted prices and assert the other type wins. Not done.
- **The golden file cannot say who made a call.** If Karpenter stopped making a call that `simctl` or the test also makes (`sqs:SendMessage`, `ec2:DescribeInstances`, `iam:GetInstanceProfile`), C8 would not notice.
- **A6 matches on NodeClaim name.** "Drained" is inferred from Karpenter deleting the node after tainting it; the eviction log line is not used, and the order is not compared with `ec2:TerminateInstances` in the trace.

## Recommendation

Continue. G0's question was whether real, unmodified Karpenter runs against a simulated AWS plane on a machine with no internet, and it does,
with a gate that has already caught real problems: the first run failed C5, C7 and C8 for the reasons above. The A6 log-order check and the isolation audit are also unit-tested against a real Karpenter log capture and against bad inspect data (garbage-collector-only removal, wrong order, a second network, a published port and a Docker socket all fail). The live gate has not been run with a deliberately broken stack.

1. Approve moving `ec2:DescribeInstanceTypeOfferings` to `ec2-sim` (33 Floci, 2 ec2-sim, 1 pricing-facade)? It widens the instance types Karpenter can use and removes the C5 workaround.
2. Continue to the next plans (Task 17: ADRs, CI, final README), or narrow scope? Narrowing needs an ADR.
